# Auth

Audit decisions for the auth actions (login, UC-02 register + email verification, UC-04 account deletion, UC-05 logout), session freshness, the password-reset and verification notifications, and the mail templates.

## Keep the auth forms strict

- `login.php`, `forgot-password.php`, and `register.php` share trim + `['required', 'email:rfc']` on email — keep them aligned; register alone adds `max:255` (the varchar column) because it is the only one that stores the address.
- The login/forgot/register pages `trim($this->email)` before `$this->validate()` (register also trims `username`), while every action trims and lowercases again at the domain boundary; validation must not reject what the action accepts — `email:rfc` rejects the padded value a paste carries, and the username regex rejects padded edges the action accepts.
- No password field is ever trimmed — not on login, register, reset, or the profile's change form. Spaces are significant password characters; trim stays an email/username concern.
- Login, reset, register, the profile change form (both the new and the current field), and delete-account re-auth cap passwords at `max:256` (bcrypt only honors 72 bytes; the bound keeps input sized). Register's email bound is load-bearing: `email:rfc` passes overlong addresses and `RegisterUserAction` only catches SQLSTATE `23xxx`, so an overlong insert would throw `22001` uncaught (a 500 on MySQL). `password_confirmation` stays unmaxed, like reset — a longer confirm surfaces as the mismatch message.

## Register has no toast re-dispatch on mount

No flow redirects to `/register` with a toast; `mount()` re-dispatching one was dead code and was removed. Don't re-add it.

## Enumeration protection on register is deliberate

- When both username and email are already taken, the error always reports "username taken" (checked first).
- Simultaneous duplicate attempts share the same IP-rate-limit bucket.

Both are intentional; keep them.

## Register's bucket is a volume cap

- `register:{ip}` counts **every** attempt — success or failure — and never clears: account creation is the volume being capped (a row plus a queued mail each), so clearing on the common path would defeat it, exactly like `verify-resend`. Login keeps `RateLimiter::clear` on success because its bucket counts failed credential guesses instead — do not align the two.
- Page-side validation failures never reach the action and therefore never count — the page does no DB or queue work before `execute()`, and uniqueness stays behind the limiter gate for the same reason (no reads while limited). The happy path stays **INSERT-first**: `User::create()` runs directly and the existence `SELECT`s fire only inside the 23xxx integrity-violation path — never add a pre-insert uniqueness pre-check (the action's query-count lock pins the request side to the insert + row reload).

## Logout returns void

`LogoutUserAction::execute()` returns `void` (no result enum) — a logout can't fail. Don't re-add a single-case result enum.

## Account deletion

- `DeleteAccountAction` orders authorize → limiter → `Hash::check` (`abort_unless($user->is(auth()->user()), 403)` first, then the bucket, then the password), so a foreign account is rejected before any bucket movement and a limited caller never reaches the hash — no oracle while limited.
- Its bucket `delete-account:{user_id}|{ip}` (5/60s) counts wrong-password re-auth guesses and clears on success — the default failure-counter shape (the delete modal is a second password-guessing surface); the clear is hygiene more than policy because the key dies with the account (a new account gets a new id). Phase-1's original "UC-04 exempt" line was corrected to match — the limiter ships.
- On success the action ends this session (`Auth::logout()` + invalidate + CSRF regenerate), forgets the session-hint cookie, scrubs the row, and soft-deletes — the page then flashes the toast and redirects home (a guest page, so the locale is reset to `config('app.locale')` first).
- **The scrub is full-scope:** email/username obfuscated to `deleted-user-{id}` / `deleted_user_{id}` (frees the unique constraints for reuse), the password replaced with junk no `Hash::check` can satisfy (a leaked row must not keep a crackable hash of a likely-reused password), `remember_token` nulled, and firstname/lastname/birthday/gender nulled. `locale`/`theme` stay — preferences, not personal data. Everything else on the row is kept for the owner FKs on tasks/plans.

## Password reset and session-hint contracts

- **Outcomes are collapsed:** exists / unknown / broker-throttled forgot and reset requests each return one generic outcome (anti-enumeration). On top of that, the broker refuses to mint a new token — and sends no email — within `auth.passwords.users.throttle` (60s) of the last one, so repeated rapid requests deliberately produce no second mail (log line: "Password reset link throttled, a token was recently created"), and `forgot-password:{ip}` caps requests at 5/60s. Both are protections, not bugs; the token row is one-per-email, so a newer send rotates the token and the previous mail's link dies.
- **Buckets:** `forgot-password:{ip}` increments on every request and never clears (clearing only real sends would leak existence via limiter timing); `reset-password:{ip}` clears on success.
- **Same-as-current:** returns `SameAsCurrent` only after `Password::tokenExists` — `Hash::check` must be unreachable without a valid, unexpired token (otherwise the form is a password oracle) and the broker must not run, so the token survives for a retry.
- **Session hint:** the 30-day cookie — name is `LoginUserAction::SESSION_HINT`; queue, forget, and consume all reference the constant — is queued at login success, forgotten at logout/account delete, and consumed once by login's `mount()` for the expired-session toast; it must outlive the 120-minute session because expiry is only detectable from outside the session. Login success regenerates the CSRF token along with the session ID before pulling `url.intended` (fallback `route('dashboard')`).
- **Reset link:** rooted at `config('app.url')` by our `resetUrl()` override on `ResetPasswordNotification` (extends the framework's `ResetPassword`, renders `mail.reset-password` with the recipient's theme variables) — never at the request `Host`, so a forged `Host` header cannot poison the link (`createUrlUsing` stays honored if ever set).
- **Reset page:** `token` and `email` are both `#[Url]` properties, so the form hydrates from the emailed link and survives a refresh; `#[Url]` hydrates from `request()->query()` **before** `mount()` runs (`SupportAttributes` registers ahead of `SupportLifecycleHooks`), so `mount()` sees both params on a real link. The email renders as the subtitle paragraph (`Resetting password for :email`, falling back to the instruction when the link carries no email) — link-provided, never user input — and an invalid or missing email maps to the invalid-link alert, never field validation (the user cannot fix a value they never typed). `mount()` checks `token` and `email` together and the form renders only while the link stays viable (`$token && $reset_error !== 'invalid_link'`) — a dead link never offers a password form.

## Password change evicts every older session

- `users.password_changed_at` (nullable) is folded into the original `create_users_table` migration — no separate migration file. Two sites stamp it alongside a remember-token rotation: `ResetPasswordAction` (emailed link) and `ChangePasswordAction` (profile modal, current password verified in the action with `Hash::check` — never the `current_password` validation rule, so the check stays frontend-agnostic like delete-account; profile's plain `password` field remains delete-account re-auth only).
- `ChangePasswordAction` also re-stamps the changing session's `auth_time` right after the save: the freshness comparison below is strictly greater-than at second precision, so without the stamp the changer would be signed out on their very next request — with it, this session survives while every older session (and other-device remember token) is still revoked. Its bucket `change-password:{user_id}|{ip}` (5/60s) counts wrong current-password guesses and clears on success — a reused current password returns `SameAsCurrent` after the current check and moves the bucket neither way (the caller already proved knowledge). Page-side validation (`required`/`confirmed`/`min:8`/`max:256`, reset's message keys) fails before the action and never counts.
- `ExpireSessionsOnPasswordChange` is appended to the `web` group in `bootstrap/app.php`, so every web request — including the Livewire update route — re-checks freshness (see `.ai/rules/wiring.md`). It stamps `session('auth_time')` on the first authenticated request lacking one (remember-me logins and sessions predating the middleware) and signs out any session whose `auth_time` predates `password_changed_at`: `Auth::logout()` + `session()->invalidate()` + token regenerate, then redirect to login with a flashed toast. Stamping rather than rejecting when `auth_time` is missing is deliberate — a recaller login must not loop-logout, and pre-deploy sessions get one free pass.

## Reset mail is localized and queued

- `User` implements `HasLocalePreference` (`preferredLocale()` returns `users.locale`), so notifications render in the account's saved language even when the guest page's app locale differs.
- The notification is queued (`ResetPasswordNotification implements ShouldQueue`, redis driver) — the worker delivers it, retries per its `--tries`, and records terminal failures in `failed_jobs`.
- `ForgotPasswordAction` wraps `Password::sendResetLink` in `try/catch (Throwable)`: anything that throws while handing the mail off (queue connection down; transport failure on the sync path/tests) is logged as an error and still returns `Sent` — an outage must not break the form or become an existence oracle.
- The mail embeds its web fonts instead of serving them: `embeddedFontUris()` on the shared `App\Notifications\Concerns\EmbedsThemeFonts` trait (used by both the reset and verification mails) base64-encodes the subsetted weights in `resources/fonts/mail/` into `data:` URIs passed to the template as `$fontUris`, so the sent HTML is a static self-contained document. A served font URL is CORS-blocked wherever email HTML renders (it is never same-origin with the app — Mailpit's view, mail clients) and would need per-environment URL/nginx/CORS setup; never point the mail at one. Weights are 400/500/600 — the exact trio the web app ships (Regular is embedded for parity even though today's markup renders only Medium body/buttons and SemiBold titles; `font-medium`/`font-semibold` are the app classes they mirror); Bold was dropped app-wide in favour of the UI's dominant semibold usage, so web and mail can never drift to a 4th weight, and the trio fits Gmail's ~102KB message-clip budget — the size and no-remote-URL contracts are pinned by the tests in `resources/views/mail/`. Regenerate after copy or font changes (tooling stays outside the repo, nothing touches `package.json`): `npm install --prefix /tmp/fontsubset subset-font`, then `NODE_PATH=/tmp/fontsubset/node_modules node resources/fonts/mail/subset.cjs`. `@font-face` support in email clients is still partial (Gmail and Word-based Outlook never load custom fonts), so the stack always ends in a Persian-safe fallback and the `mso-generic-font-family`/`mso-font-alt` pairs keep Word-based Outlook on Tahoma instead of Times New Roman.
- Branding: the card header reuses the app's `<x-mine.brand-logo>` component (inline SVG, `currentColor` tinted by `var(--mine-btn-primary-bg)` — the same rule as `.ai/rules/mine.md`, never `<img>`), centered by `.content { text-align: center }`. The logo is the mail's only brand mark: clients that strip inline SVG (Gmail, Word-based Outlook) show no visible brand — the app name survives only as the SVG's `aria-label` — accepted by design.

## Email verification

- **Model + notification:** `User implements MustVerifyEmail` (the contract — the trait methods come from `Illuminate\Foundation\Auth\User`) and overrides `sendEmailVerificationNotification()` to push our `VerifyEmailNotification` (queued, `HasLocalePreference` via `User`, renders `mail.verify-email` on the reset mail's shell and shared font trait, colored with the **app default theme** via `defaultThemeVars()` — a verification targets a brand-new account that never chose one; only the reset mail follows the recipient's theme). No `Registered`/`Verified` events exist (`.ai/rules/actions.md`) — the verify route marks the account through `VerifyEmailAction`, which stamps and logs.
- **Link:** `verificationUrl()` signs a **relative** URL (`URL::temporarySignedRoute(..., $absolute = false)`) and roots it at `config('app.url')` — same Host-poisoning reasoning as `resetUrl()`. The route must therefore validate with `signed:relative`, which HMACs path + query only: the link keeps validating wherever APP_URL points, and a forged `Host` can never poison it. Expiry is the framework default `auth.verification.expire` (60 minutes); `createUrlUsing` stays honored.
- **Routes and gating:** `verification.notice` (`/email/verify`, `pages::auth.verify-email`) and `verification.verify` (`/email/verify/{id}/{hash}`, `['auth','signed:relative']`, framework `EmailVerificationRequest` authorizes the id + sha1 hash against the signed-in account, so a valid link opened by any other account is a 403 — pinned) both sit in the `auth` group and are deliberately **not** `verified`-gated — the notice page is the gate's redirect target and must stay reachable, and logout lives there too. The six app pages carry `['auth','verified']`; logout stays `auth`-only and the Livewire update endpoint is never verified-gated (the notice page's resend runs through it).
- **Auth surfaces render on the app default theme:** `layouts/auth.blade.php` passes `:theme="config('themes.default')"` into `x-mine.theme-vars` (mechanism in `.ai/rules/config.md`) — auth pages are pre-personalization, so the notice page never shows a saved theme; locale stays per-account via `HasUser`. The subtitle is tense-neutral ("Open the verification link in your :email inbox" — no send-time claim, the page may open long after register) and the footer mirrors the other auth pages' prompt + link row ("Not your account?" → Log out, POST through fetch).
- **Register dispatch:** `RegisterUserAction` calls `$user->refresh()->sendEmailVerificationNotification()` inside `try/catch` after the account row exists — `User::create()` only returns the INSERTed columns, so without the reload `locale` (DB default, never inserted) is missing and `preferredLocale()` TypeErrors on `null`. The row itself lands with `email_verified_at` NULL — the gate's whole premise (pinned). Any dispatch failure is logged and still returns `Success`; the notice page's resend is the recovery path.
- **Resend:** `ResendVerificationAction` with bucket `verify-resend:{user_id}|{ip}`, 5/60s — like `forgot-password:{ip}` it **never clears** (clearing successful sends would defeat the volume cap, success being the common path); `available_in` is logged for rate-limited outcomes, a hand-off failure is logged and still returns `Sent`, and `AlreadyVerified` short-circuits without mail. Outcomes render as in-page state on the notice page (`resend_error = 'rate_limited'` alert; success is a direct toast dispatch), never flash toasts.
- **Verify outcomes:** `VerifyEmailAction` returns `Verified` (marks + logs) or `AlreadyVerified` (leaves the timestamp untouched, no toast); the route closure flashes the success toast and redirects to the dashboard. Guests opening the link ride UC-1's intended-URL login straight back to it — the composed journey (guest GET → `url.intended` → sign-in → return → verified) is pinned in `VerifyEmailLinkTest`.
